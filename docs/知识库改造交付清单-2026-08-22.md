## 1. 完整计划与方案

### 1.1 目标

把 DSH 工作台的知识库从“前置注入”升级为“AI 自决的自适应检索系统”，形成正反馈闭环：用 AI 做项目 → 壮大知识库 → 反哺 AI。核心原则：知识库是优先证据源而不是唯一来源；每一步都由“信号”驱动而不是写死；所有行为可配置、可评测、可回退。

### 1.2 总体架构（数据流）

用户提问 → M1 意图与门控 → M2 路由与召回 → M3 召回后处理 → M4 覆盖评估与联网兜底 → M5 生成 → M6 生成后审计 → 交付 → M7 自生长闭环；M8 上下文/成本治理贯穿；M9 评测与验收把关。

### 1.3 九个功能模块（M1-M9）

| 模块 | 内容 |
|---|---|
| M1 门控 | 规则门控（寒暄零成本跳过）→ 知识型判定 → 模型自决是否调用工具；模式 `rule | model | both` |
| M2 路由召回 | 复杂度路由三档：简单走一次混合检索；模糊/长问题向量优先+查询改写；复杂多跳最多 2 轮迭代检索 |
| M3 后处理 | 重排（默认关）→ 置信度过滤 → 选择性压缩（token 预算）→ 去重 |
| M4 覆盖与联网 | 覆盖信号三级：充分只查库、灰区知识库+Web 并行、不足以 Web 为主；冲突并列呈现 |
| M5 生成约束 | 强制内联引用 `[知识N《标题》· 置信度X]`；网页内容带可点击 URL；可标注“未验证” |
| M6 引用审计 | 引用真实性校验（每个引用必须真实存在）；可升级逐句 groundedness；失败修正或 abstain |
| M7 自生长 | 未命中进候选池 → 蒸馏 → EDV 验证 → 入库；经验快照沉淀；引用反馈调置信度；真实问题沉淀为评测题 |
| M8 成本治理 | 工具卡片注入、10 分钟会话缓存、精简 schema、快速路径跳过重排/迭代 |
| M9 评测 | 50 题离线评测 + 在线 trace 评分 + 成本/延迟指标 + 回归门禁 |

### 1.4 实施路线（S0-S5）

S0 规格确认 → S1 工具插件原型（knowledge_search/knowledge_read 接入 agent）→ S2 路由/迭代/覆盖/联网兜底 → S3 引用审计+评测套件 → S4 自生长+配置面板 → S5 全量回归交付。

### 1.5 验收标准（原方案 8 条）

1. AI 自行调用知识库并带 `[知识N《标题》· 置信度X]` 引用；
2. 知识库+最新业界做法时主动联网补充并带 URL；
3. 知识库没有的问题不硬编，能联网就联网，不能就标“未验证”；
4. 寒暄 0 检索、0 额外 token；
5. 不污染上下文（用户消息原文不被改写）；
6. 每个引用真实存在，无证据句子被标注；
7. 自生长：一段时间使用后条目数/recall 上升，未命中进候选池；
8. 全流程：recall@5 ≥ 0.9、groundedness ≥ 0.85、abstain 率可接受、单次检索成本可控。

### 1.6 实际采用的默认配置（当前源码）

`plugins/workbench/lib/host/index.js` 中 `KNOWLEDGE_AUTO_DEFAULT_CONFIG`：

- `gate: 'both'`（规则门控 + 模型自决）
- `routing: 'auto'`、`maxIterations: 2`
- `topK: 3`、`tokenBudget: 600`
- `rerank: 'none'`（可选 `local`/`llm`）
- `webFallback: true`、`thresholds: { insufficient: 0.42, gray: 0.55 }`（R1 校准值）
- `auditLevel: 'ref-only'`
- 缓存 TTL 10 分钟

## 4. 根因判断：是不是知识库改造造成的？

1. **是（已修复）**：发送卡顿、浮窗残留、第三条消息卡死、`knowledge entry is not published` 报错，都是 KB 改造期间引入或暴露的（发送前自动检索拦截器、旧条目状态兼容），均已修复并有回归测试。

## 6. 最终根因与修复（2026-08-22 已定位并解决）

### 6.1 根因（两个 bug 同源）

**工作台插件客户端为每个打开的会话创建一条永久 SSE 长连接（`/api/dsh-workbench/events?sessionId=...`），切换会话时从不关闭，导致连接泄漏。**

- 位置：`plugins/workbench/lib/client.js` 的 `wbTaskEventSources`（任务中心事件流）。
- 机制：每激活一个会话就 `new EventSource(...)` 并存入 Map，取消订阅只删监听器、不 `close()`；官方运行时自身还常驻 2 条 SSE（`events.mux` + `events.host`）。打开 3 个会话后：3 条泄漏 + 2 条官方 = 5 条长连接，第 4 个会话的请求排不进 Chromium 同源 6 连接上限 → 排队 30 秒后被 `AbortSignal.timeout` 中止。
- 现象吻合：“signal timed out”是 Chromium 对超时中止 fetch 的文案；`(internal)` 是 RPC 错误码；重启后前 3 个正常、第 4 个卡死；新建会话同样走大量 HTTP 请求，因此第 4 个新建也会卡死且后续点击“无反应”（上一次创建的 Promise 未结束，`creatingSessionRef` 一直为 true，静默拦截后续点击）。

### 6.2 修复内容

1. **事件流只保留当前会话一条**：`wbEnsureTaskEventSource` 在创建新会话流前关闭并删除旧会话流；监听器清空时关闭全部流。改动后渲染进程到 host 的长连接保持有界（2 条官方 + 最多 1 条工作台）。
2. **新建会话不再静默失败**：`newSession` 改为必选工作区校验；优先 `workspaces.connectWorkspace`（复用空白会话），不可用时回退官方 `sessions.create`；失败时明确提示而不是无响应；`finally` 始终复位 `creatingSessionRef`，避免“点了没反应”。

### 6.3 验证结果（真实桌面端 + 自动化）

- 修复前（同一台机器、同一数据）：
  - 顺序/并发直连 host 历史请求：66-145ms 全部成功。
  - 渲染进程打开第 4 个会话：`session.history` 发出后 30 秒无响应；后续请求全部 `ERR_ABORTED`；界面报 `历史加载失败：signal timed out`。
  - 渲染进程自发的 `session.list` 请求：6 秒超时（`TimeoutError: signal timed out`），而同一时刻外部直连 host 87ms 成功 → 确认是渲染进程连接池被占满。
  - TCP 连接：渲染进程到 host 8 条 Established，连接池饱和。
- 修复后：
  - 连续打开 20 个历史会话：0 失败，全部 200 于 90-110ms 返回。
  - 新建会话流程：进入空白会话、无超时、无报错（复用空白会话为正常设计）。

### 7.2 确认的“表层修复”与跨功能干扰

1. **任务事件流无清理（本次 bug 根因）**：任务中心新增事件流时只做了“创建+订阅”，没做“切换时关闭”，属于典型的表层实现；跨功能影响最大。
2. **会话创建链路反复修补**：8/21 的会话中为“第 4 个会话失败”连续修改了客户端打开去重、等待绑定、失败重试、串行队列、切换锁，都是围绕症状打补丁；真正的连接泄漏直到本次用 CDP 抓网络才定位。前序尝试的“AbortSignal 传递、历史裁剪、串行队列”虽属合理加固，但不是根因。
3. **`sessions.create` 误用**：曾把 RPC 结果对象当会话 ID，属于表层修复后遗留的调用错误，已纠正。
4. **风格页只改了一半**：风格系统存在半成品状态（用户已知），与本次两个 bug 无直接关系，但属于需要单独收尾的模块。
5. **官方运行时会话实例不释放**：`Session.dispose()` 空实现、`followCurrent()` 不释放旧会话，属上游内存面问题；dropScope 补丁已部署，属于预防性加固而非本 bug 根因。

### 7.3 结论

两个 bug 均非知识库检索功能本身导致，而是**工作台插件客户端的事件流/会话管理代码在开发过程中引入了连接泄漏与静默失败**。修复已部署，无需重构官方核心或桌面壳；若后续做深度模块审计，建议优先级：任务中心事件流（已修）→ 会话面板/新建流程（已加固）→ 风格页收尾 → 官方运行时内存释放（dropScope 验证）→ 独立仓库 `dsh-workbench` 依赖同步。
