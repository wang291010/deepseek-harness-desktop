# 工作台会话蒸馏完整方案（第二版实施稿）

> 日期：2026-08-24  
> 状态：十项决策全部确认；P6.1 已于 2026-08-24 完成首版实施、自动化验证与桌面部署  
> 范围：右侧工具栏「蒸馏」页签；“工作台专家设计”另开议题，不在本文展开

## 1. 推荐结论

把“会话蒸馏”定义为一个**有来源、可编辑、可去重、可回滚的知识候选审核流程**，而不是普通的会话总结按钮。

推荐首版采用以下默认策略：

1. **手动触发、后台处理**：用户在右栏选择范围后点击蒸馏，不影响当前对话响应速度。
2. **按原子知识提取**：一条候选只表达一个偏好、决策、知识点、经验、方法或开放事项。
3. **先比对再写入**：先检索现有知识库，给出 `新增 / 合并 / 更新 / 取代旧版本 / 跳过` 建议。
4. **人工逐条确认**：模型只提出候选和操作建议，不自动发布。
5. **只进入 `01-Inbox`**：沿用项目现有审核机制，审核后再进入 `02-Atomic`。
6. **保留证据和历史**：每条候选记录来源会话、消息范围、蒸馏批次和时间；矛盾事实不静默覆盖。
7. **首版不引入图数据库**：在现有 Markdown 知识库、检索和预检能力上实现；等数据量和关系查询需求证明必要后，再评估时序知识图谱。

一句话产品定义：

> 从当前会话的指定范围中，提炼值得长期保留的原子知识，与既有知识进行去重和冲突检查，经用户确认后写入知识库草稿区。

## 2. 当前现状与缺口

### 2.1 已有能力

- 右侧工具栏已有「蒸馏」页签，但 `ToolbarDistill` 仍是“建设中 · P6”的禁用占位页。
- 已有 `/api/dsh-workbench/knowledge/distill`，能把用户粘贴的文本转换为 `note / experience` Markdown，并写入 `01-Inbox`。
- 知识条目已有 `confidence`、`claimType`、`staleness`、`assumptions`、`related`、`status=review` 等元数据，以及入库前预检和人工审核机制。
- 已有“记忆快照”，但它只压缩一次多代理编排的结果，不读取普通会话。
- 客户端可以通过官方 Session binding 获得当前会话实例，宿主侧的执行上下文也能访问 session events。

### 2.2 核心缺口

- 不能选择并读取“当前整段 / 最近若干轮 / 自上次蒸馏以来”的会话。
- 一次调用只生成一篇 Markdown，不能输出多条原子候选。
- 没有候选预览、逐条编辑和选择。
- 没有与既有知识进行语义去重、合并和矛盾检查。
- 没有来源消息、批次、游标和写入结果的完整审计链。
- 没有幂等保障；重复蒸馏同一范围可能产生重复条目。
- 没有敏感信息过滤、推断事实标记和过期策略。

因此，现有知识蒸馏接口可以复用部分格式化和入库能力，但不能直接充当会话蒸馏后端。

### 3.1 第二轮调研带来的方案优化

1. **把“更新”拆细**：新内容否定旧内容用 `SUPERSEDE`，只增加细节用 `MERGE`，当前状态补全才用 `UPDATE`，避免一个含糊的 UPDATE 包办所有变化。
2. **增加“知识点”类型**：概念、原理、比较、约束和可引用结论，不应硬塞进经验或方法。
3. **增加模板层**：范围选择之外，再选择“自动 / 技术讨论 / 故障复盘 / 需求评审 / 学习笔记”，模板只影响提取重点，不改变安全与审核门槛。
4. **增加单条晋升入口**：除批量蒸馏外，未来可在某条高价值回复旁提供“提炼为知识候选”，仍需预检和审核。
5. **画像与专家彻底解耦**：画像描述用户，专家描述 AI；蒸馏器不能通过画像同步改写专家人格或工具权限。
6. **后台自动化只做发现**：即使以后定期回顾，也只生成候选提醒，不自动提交知识。

## 4. 蒸馏对象与知识分类

### 4.1 应提取的六类候选

1. **用户偏好 `preference`**
   - 例：回复应先给结论；喜欢先出方案再执行。
   - 只保存用户明确表达，或用户明确确认过的偏好。
2. **项目事实与决策 `decision`**
   - 例：会话蒸馏首版只写入 `01-Inbox`；阶段 F/G/H 暂停。
   - 必须包含适用项目、上下文、决策理由、状态和时间。
3. **经验案例 `experience`**
   - 例：某次故障的症状、原因、采取的动作、验证结果和适用边界。
   - 只有存在真实结果或验证证据时才进入长期知识。
4. **可复用方法 `procedure`**
   - 例：触发条件、步骤、检查点、失败回退和适用限制。
   - 不能只写抽象口号，必须可执行、可验证。
5. **知识点 `knowledge`**
   - 例：OpenAI compaction 解决长对话上下文成本，不等同于面向人的长期知识蒸馏。
   - 用于概念、原理、比较、公式、限制或有证据支持的通用结论；必须记录来源、适用边界和时效。
   - 只在会话中确实形成、引用或验证过时提取，不能凭模型常识额外扩写一批“百科知识”。
6. **开放事项 `open_loop`**
   - 例：待单独讨论“工作台专家设计”。
   - 默认进入任务/会话待办，不进入长期知识库；完成或失效后关闭。

### 4.2 不应提取的内容

- 问候、寒暄、重复确认、无后续价值的临时对话。
- 模型自己的猜测、未被用户确认的性格或身份推断。
- API Key、密码、令牌、Cookie、私钥及其他凭据。
- 与未来工作无关的长段原文、完整代码输出、工具噪声。
- 只有“计划做”但没有结果的内容，不得写成“已验证经验”。
- 很快过期且没有复用价值的信息；若确需保留，必须设置 `validUntil`。

### 4.3 一条合格原子知识的标准

候选必须同时满足：

- **单一性**：只表达一个核心结论。
- **持久性**：未来会话仍可能有用，或能避免重复踩坑。
- **可证实性**：能定位到来源消息，事实和结果有证据。
- **作用域明确**：属于用户、项目、专家还是全局知识。
- **时间明确**：稳定、需复核、易变化，必要时有有效期。
- **可操作性**：经验和方法写清适用条件与验证方式。

## 5. 蒸馏规则

### 5.1 来源可信度

来源按优先级处理：

1. 用户明确陈述或明确批准；
2. 工具返回、测试结果、文件和日志中的可验证事实；
3. 助手结论且被用户认可；
4. 助手单方面建议；
5. 模型推断。

第 1—3 类可成为 `fact`；第 4 类只能成为建议或待办；第 5 类默认跳过，确有价值时标为 `hypothesis` 并要求人工确认。

### 5.2 操作判定

每条候选与既有知识比对后，只能提出以下动作：

- `ADD`：没有等价旧知识，新增草稿。
- `MERGE`：语义相同，新内容只补充证据、条件或细节。
- `UPDATE`：同一对象的当前状态需要补全，但不否定旧内容。
- `SUPERSEDE`：新事实明确取代旧事实；旧条目标为失效并保留历史。
- `SKIP`：重复、低价值、无证据、敏感、过度推断或不够稳定。

首版不提供自动 `DELETE`。删除知识必须由用户在知识库管理界面单独执行。

### 5.3 冲突与时效

- 相同主题出现矛盾时，优先比较来源等级和时间。
- 用户明确更正自己的旧偏好时，建议 `SUPERSEDE`。
- 无法判断新旧真假的，显示“冲突待确认”，不得自动写入。
- `staleness` 沿用现有 `STABLE / CHECK / VOLATILE`。
- 临时事实可加 `validFrom / validUntil`；到期后不参与默认召回，但保留审计记录。

### 5.4 去重与幂等

按三层判定：

1. **来源幂等**：同一 `sessionId + rangeHash + extractorVersion` 重跑时复用原批次。
2. **词面归一**：去空白、标点差异、大小写和常见格式差异。
3. **语义比对**：检索相似条目，再由判定器结合对象、谓词、作用域和时间判断。

不能只凭向量相似度直接合并；“喜欢深色主题”和“当前项目使用深色主题”相似但作用域不同。

### 5.5 隐私与安全

- 蒸馏前本地规则扫描凭据和高风险敏感字段；命中后默认遮盖并阻止写入。
- 不从语言风格推断健康、政治、宗教、性取向等敏感属性。
- UI 必须显示最终将发送给模型的范围和大致字符/Token 数。
- 原始会话继续由原会话系统保存；蒸馏账本只保存消息 ID/序号和必要证据片段，不复制整份聊天。
- 所有写入都受现有项目路径校验、非符号链接检查和原子写保护约束。

## 6. 完整用户流程

### 6.1 入口状态

右侧「蒸馏」页签显示：

- 当前会话标题和项目；
- 总轮数、可蒸馏轮数；
- 上次成功蒸馏位置和时间；
- 当前知识库目标（默认当前项目的 `01-Inbox`）；
- “选择范围”与“开始分析”。

无会话、历史未加载、只有寒暄或正在蒸馏时，给出明确状态，不显示无效按钮。

### 6.2 范围选择

提供三种范围：

1. **自上次蒸馏以来（默认）**：增量、成本最低。
2. **最近 N 轮**：默认 20 轮，可调。
3. **自定义起止消息**：适合只蒸馏某个专题。

首次使用默认“当前全部有效对话”，但应显示字符/Token 估算；超出阈值时自动按语义段落切块，最终仍作为一个批次审核。

### 6.3 分析过程

状态顺序：

`读取会话 → 清理与分段 → 提取候选 → 查询旧知识 → 去重/冲突判定 → 安全检查 → 等待审核`

任务进入官方 Job Panel，支持进度展示和取消。取消时不得留下半写入条目。

### 6.4 审核界面

候选按类型分组，每张卡片显示：

- 标题和原子正文；
- 类型、作用域、置信度、时效；
- 建议动作 `新增 / 合并 / 更新 / 取代 / 跳过`；
- 来源会话与可展开的证据片段；
- 相似旧条目、差异和冲突说明；
- “选中、编辑、修改类型、查看原文、跳过”。

顶部显示汇总：`共 8 条：新增 3、合并 2、更新 1、冲突 1、跳过 1`。

底部主按钮：**“将选中项保存到 01-Inbox”**。不得使用含糊的“完成”按钮。

### 6.5 写入与结果

用户确认后才进行写入：

- 每条候选单独生成 Markdown 草稿；
- 写入成功后记录目标路径和内容哈希；
- 批次全部成功后推进会话蒸馏游标；
- 部分失败时不推进游标，展示可重试项；已成功项靠哈希保持幂等；
- 结果页提供“打开知识库草稿”“查看蒸馏历史”“撤销本批次”。

撤销只撤销本批次新建且未被后续修改的草稿；合并/更新类操作首版建议也生成新草稿和关系建议，不直接改 `02-Atomic`，因此可安全撤销。

```text
│ [保存 4 条到 01-Inbox]           │

```

首版建议使用右栏内的步骤式界面；候选较多时打开宽抽屉。不要把所有审阅内容硬塞进窄栏。

## 9. 技术方案

### 9.1 总体结构

```text
当前 Session events
        ↓
会话读取与标准化（只保留 user/assistant/tool 的可见必要内容）
        ↓
敏感信息扫描 + 语义分段
        ↓
结构化候选提取器
        ↓
现有知识检索 / 预检
        ↓
动作判定器（ADD/MERGE/UPDATE/SUPERSEDE/SKIP）
        ↓
右栏人工审核
        ↓
现有 Markdown 生成与 01-Inbox 写入
        ↓
批次账本 / 游标 / 审计 / 撤销
```

### 9.2 会话读取

- 客户端 `ToolbarDistill` 接收 `sessionId` 和 `projectPath`。
- 通过官方 session binding 确认历史已打开，并取得稳定的事件范围标识。
- 具体的宿主 API 在实施前需用当前 rc.2 的公开 runtime 类型再核实一次；禁止扫描 Codex 私有数据库或猜测内部文件路径。
- 标准化时保留角色、文本、时间、turn/step、工具结果摘要；隐藏模型内部推理和无关的大型二进制附件。

### 9.3 新接口建议

- `POST /api/dsh-workbench/distill/analyze`：创建批次并注册后台 Job。
- `GET /api/dsh-workbench/distill/run?id=...`：读取进度、候选和错误。
- `POST /api/dsh-workbench/distill/review`：保存用户编辑和选择。
- `POST /api/dsh-workbench/distill/commit`：把选中项写入 `01-Inbox`。
- `POST /api/dsh-workbench/distill/cancel`：取消分析或写入前任务。
- `POST /api/dsh-workbench/distill/undo`：撤销满足安全条件的本批次新草稿。
- `GET /api/dsh-workbench/distill/history?sessionId=...`：查看批次和游标。

### 9.4 存储

- 新增独立账本，例如 `dsh-workbench-distill.json`，保存批次、候选、游标和写入映射。
- 继续使用现有知识库目录保存最终草稿，不重复建设第二套知识库。
- 写入采用临时文件 + 原子 rename；账本设置体积上限、版本号和迁移函数。
- 候选证据只留短片段和事件定位，避免账本复制全量会话。

### 9.5 模型处理链

推荐三次受约束调用，而不是一次“大提示词包办”：

1. **提取**：仅根据来源生成结构化候选；宁缺毋滥。
2. **协调**：带候选和检索到的旧知识，判定动作、冲突和时效。
3. **成稿**：只对用户选中项生成符合现有 frontmatter 的 Markdown。

每一步都使用 JSON Schema 校验、长度限制、失败重试和确定性回退。模型不可直接获得文件写权限。

### 9.6 与现有能力的关系

- 复用知识库扫描、搜索、预检、frontmatter、`01-Inbox` 和质量配置。
- 将现有 `distillKnowledge` 拆出“Markdown 成稿”纯函数供 commit 阶段复用；不要让 analyze 阶段提前写文件。
- 记忆快照仍服务于多代理编排上下文，不与会话蒸馏账本混存。
- `open_loop` 可在后续与任务中心打通，首版先只展示/导出，不自动创建任务。

## 10. 分阶段实施建议

### P6.1：可用闭环（已实施）

- 读取当前会话和三种范围。
- 后台 Job + 取消。
- 六类候选和结构化证据。
- 现有知识检索、词面/语义去重。
- `ADD / MERGE / UPDATE / SUPERSEDE / SKIP` 建议。
- 右栏/宽抽屉审核、编辑和选择。
- 只写 `01-Inbox`，批次审计、游标、幂等和安全撤销。
- 敏感信息扫描和拦截。

### P6.2：质量与维护

- 跨批次冲突链、有效期和旧版本失效。
- 蒸馏历史、重新分析、失败项重试。
- 单独设计用户画像的数据结构、可见管理页、权限和注入预算；通过独立评审后再考虑受控同步。
- 从审核反馈统计误提取和误合并，迭代规则。

### P6.3：智能建议（有数据后再做）

- 会话长时间空闲或关闭时，仅提示“发现 N 条可蒸馏候选”。
- 周期性合并低粒度条目、发现重复模式。
- 评估是否需要时序知识图谱。
- 仍不自动发布到 `02-Atomic`。

## 11. 验收测试矩阵

| 场景 | 预期结果 |
|---|---|
| 纯问候和闲聊 | 0 条候选，并说明没有值得长期保存的内容 |
| 用户明确偏好 | 生成 `preference`，来源为用户消息 |
| 用户更改旧偏好 | 建议 `SUPERSEDE`，旧条目保留且标记失效 |
| 重复表达同一事实 | `MERGE` 或 `SKIP`，不得新增重复文件 |
| 相似措辞但作用域不同 | 不错误合并，显示用户/项目作用域差异 |
| 项目决策含理由 | 生成 `decision`，带上下文、理由、时间和证据 |
| 对话形成通用概念或比较 | 生成 `knowledge`，带结论、来源、适用边界和时效 |
| 模型凭常识扩写会话未提及内容 | 不生成知识点，或标为无来源并阻止写入 |
| 故障修复有测试结果 | 生成 `experience`，含症状、原因、动作、结果、边界 |
| 只有修复计划、尚未验证 | 不写成经验；归为 `open_loop` 或跳过 |
| 方法可复用 | 生成 `procedure`，含触发条件、步骤、验证和回退 |
| 对话含密钥 | 候选被遮盖并阻止写入 |
| 同范围重复蒸馏 | 复用批次或得到 0 个新增，不产生重复草稿 |
| 分析途中取消 | Job 终态 cancelled，无候选落盘到知识库 |
| 写入部分失败 | 游标不推进；重试不会重复写成功项 |
| 撤销批次 | 只移除未被后续改动的本批次草稿，审计记录保留 |
| 来源回看 | 能定位会话和证据片段，内容哈希一致 |

自动化至少覆盖：规则单测、Schema 契约、幂等、原子写、冲突策略、敏感信息拦截、API smoke、右栏 GUI E2E、安装包哈希一致性。

## 12. 质量指标

上线后按批次记录，不记录敏感原文：

- **候选接受率**：用户最终选中的候选 / 总候选。
- **无需编辑率**：原样通过候选 / 已接受候选。
- **误合并率**：被用户从合并改为新增或跳过的比例。
- **重复率**：写入后被判为重复的条目比例。
- **来源覆盖率**：有有效证据定位的候选比例，目标 100%。
- **冲突正确率**：冲突样本中正确提示的比例。
- **幂等通过率**：同范围重跑无重复，目标 100%。
- **平均耗时和 Token**：按会话长度分桶。
- **后续召回价值**：蒸馏知识被检索并被答案引用/采用的比例。
- **撤销率**：高撤销说明规则或审核界面需要调整。

建议先收集 20—30 个真实批次，再决定是否启用自动候选提示。

## 13. 风险与应对

| 风险 | 应对 |
|---|---|
| 模型把建议写成事实 | 来源等级 + `claimType` + 用户审核；未确认推断默认跳过 |
| 知识碎片过多 | 原子提取上限、重要性门槛、合并建议、批次质量指标 |
| 旧知识被错误覆盖 | 首版不直接改 Atomic；使用 SUPERSEDE 草稿和人工确认 |
| 长会话成本高 | 增量游标、分段、候选上限、后台 Job、Token 预估 |
| 敏感信息泄露 | 本地预扫描、遮盖、阻断、最小证据片段 |
| 会话 API 随官方升级变化 | 只使用公开 session/runtime 能力；加契约测试和版本兼容层 |
| 取消时部分写入 | analyze/commit 分离；commit 原子化；成功项哈希幂等 |
| “摘要”和“知识”概念混淆 | UI 明示：摘要用于继续对话，蒸馏用于长期知识库 |

## 14. 用户画像、专家预设与知识库的边界

### 14.1 三者分别回答什么问题

| 对象 | 回答的问题 | 典型内容 | 作用域 | 使用方式 |
|---|---|---|---|---|
| 用户画像 | “用户是谁、长期偏好和约束是什么？” | 称呼、表达偏好、审批习惯、稳定目标、明确禁忌 | 跨项目、跨专家；属于用户 | 少量高频上下文，或按需读取 |
| 专家预设 | “AI 应该是谁、怎样工作、能用什么？” | 角色、性格、职责、工作流、技能、工具权限 | 某个专家；新会话选择 | 注入 `agent.cordis.yml` 与 `preset.yml` |
| 知识库 | “什么是真的、发生过什么、如何解决？” | 知识点、项目决策、经验、方法、证据 | 个人/项目/全局知识域 | 检索后按需读取和引用 |

工作台当前已经有“专家预设”和“个人/项目知识库”，但**没有独立的用户画像子系统**。因此，原决策 9 中的“用户画像”是建议新增的未来能力，不是专家页已有字段的别名。

### 14.2 和专家板块的关键区别

- 用户画像描述的是**你**；专家预设描述的是**AI**。
- “用户喜欢先看方案再执行”属于用户画像；“你是严谨的架构师，先列风险再设计”属于专家预设。
- 用户画像可以被多个专家读取；专家的人格、工具和技能不会反向变成用户事实。
- 切换专家不应改变用户画像；修改用户偏好也不应静默修改所有专家配置。
- 某个专家特有的交互约定，例如“只在法律专家中使用正式语气”，应留在该专家预设，不进入全局用户画像。

### 14.3 推荐的数据流

```text
会话蒸馏候选
  ├─ 知识点/决策/经验/方法 → 01-Inbox → 审核 → 知识库
  ├─ 开放事项               → 待办候选（不入知识库）
  └─ 稳定用户偏好           → 画像候选（单独确认）→ 用户画像
                                                   ↓ 只读授权
                                               各专家按需使用
专家预设 ── 人工创建/编辑 ──────────────────────────┘
```

关键规则：蒸馏器可以提出“画像候选”，但不能修改专家的性格、技能、工具和权限；专家只能读取用户授权的画像字段。

### 14.4 对决策 9 的修订建议

推荐改成：

> **P6.1 不建设或同步用户画像，只把稳定偏好作为 `preference` 候选写入 `01-Inbox`；P6.2 另做用户画像方案和可见管理页。届时只有用户明确勾选“同步到我的画像”后才更新，专家预设永不被会话蒸馏自动修改。**

理由：当前还没有画像数据结构、查看/删除界面、字段权限和注入预算。把它塞进首版会扩大范围，也容易让用户偏好、专家人格和项目知识互相污染。
