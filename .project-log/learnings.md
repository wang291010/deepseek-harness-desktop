## C0085 · 技能迁移应提供独立可执行说明

- 场景/触发词：另一套工作台 / 旧版 skill / 同步更新 / 迁移说明 / 两份副本
- 做了什么：将 skill 的行为变化、文件路径、更新步骤、验证命令和回滚方式集中写入独立 Markdown，避免依赖原始对话上下文。
- 结果：工作台可按文档逐项替换三个旧版 `SKILL.md`，并验证 UTF-8、frontmatter、哈希和关键规则。
- 评价：跨环境同步时，差异清单和验收标准比只复制最终文件更可靠；文档应明确哪些内容是 skill 规则、哪些内容属于项目自身日志。

## C0086 · 发布提交与构建产物必须分开

- 场景/触发词：上传现有修改、Windows 安装包、artifacts、provider 压缩包、发布前清理。
- 做了什么：源码和日志进入 Git 提交候选；`dist/` 安装器只作为发布产物保留；`artifacts/` 中的 provider 二进制、压缩包和截图明确不加入提交。
- 结果：`dist:win` 在提升权限后完成全套 Windows 发布门禁，生成未签名 x64 NSIS 安装包并通过 PE 校验；普通权限失败原因是 node_modules ACL，而非构建代码错误。
- 评价：发布前先检查 Git 状态和忽略规则，避免把本地验收材料、用户数据或大体积 provider 归档误上传。

## C0087 · 上传后必须核对远程资产哈希

- 场景/触发词：GitHub Release、覆盖旧安装包、上传完成、下载地址、SHA-256。
- 做了什么：使用 `gh release upload --clobber` 覆盖 `v2.1.1` 同名资产，并通过 GitHub API读取远程资产大小、状态、digest 和下载地址。
- 结果：远程资产状态为 `uploaded`，远程 digest 与本地安装包 SHA-256 完全一致；源码 `eab2c9c` 同步在 `origin/main`。
- 评价：上传命令成功不等于资产可用，必须再读 Release API 对比远程大小和 digest，尤其是覆盖同名资产时。

## C0084 · AI 项目日志应采用地图式渐进披露

- 场景/触发词：上下文污染 / project-log 优化 / AI coding agent / 全文读取 learnings / 技能副本漂移
- 做了什么：参考 2026 年 OpenAI Harness Engineering、Claude Code、Cursor、Gemini 等 AI 编程实践，把日志访问改为“项目概况 → status/index 路由 → 相关详情”；将蒸馏改为只处理未标记条目，并统一重复技能副本和 `draft` 状态语义。
- 结果：普通任务默认不加载完整 changelog/learnings；蒸馏按批次增量读取；六份技能格式校验通过且副本哈希一致。
- 评价：短地图和可检索索引比大型常驻说明更适合 AI；先改读取边界和路由，不必立即引入向量数据库或迁移全部历史格式。

## C0060 · 配置约束必须以桥接运行时为最终准绳

- 场景/触发词：MCP reconnect / `maxAttempts=0` / stdio 集成 / Streamable HTTP 集成 / 官方客户端契约
- 做了什么：直接核对官方 `dsh-mcp-client` 的 Schemastery 与 transport 实现，把桌面设置的 `maxAttempts` 下限改为 1；新增本地临时 JSON-RPC MCP 服务，分别经官方 stdio 与 Streamable HTTP transport 验证工具发现、命名、调用和释放。
- 结果：两条真实本地传输集成均通过，工具名稳定为 `mcp__<serverName>__<rawName>`，释放后注册表为空；全量测试剩余失败均是 Windows/macOS 环境模拟差异，不是 MCP 链路失败。
- 评价：配置 Schema 只能证明“能保存”，官方桥接实际解析和 transport 集成才能证明“能运行”；自动化优先使用本地无密钥 MCP 服务，避免把网络和用户配置引入测试不确定性。

## C0059 · 严格类型检查应覆盖 Schemastery 默认值和 JSX 原生事件

- 场景/触发词：MCP 重连字段 / tsc 严格模式 / `exactOptionalPropertyTypes` / JSX `event implicitly any`
- 做了什么：在提升权限可读依赖后运行 Host/Client TypeScript 检查，修复嵌套 Schemastery 对象默认值必须完整、profile 缺失设置的显式空数组、未知 servers 输入归一化、patch optional 类型和 JSX runtime 下原生控件事件无上下文类型等问题。
- 结果：Host 与 Client 类型检查通过，MCP 单测 4/4，profile/package 回归 30/30，手动 build 流程成功；独立 Web 启动探针仍因 `window.__DSH_BOOT__` 缺失失败，未与 MCP 编译结果混淆。
- 评价：新增配置字段后不能只跑业务单测；`z.object(...).default({})` 在严格泛型下可能不成立，`jsx()` 工厂也不会像 JSX 语法一样自动推断事件参数。应先跑 Host/Client 双 tsc，再做运行时启动探针。

## C0058 · 源码模块分开、安装包统一、数据根目录集中

- 场景/触发词：MCP 不并入工作台 / 是否新建插件 / 安装包从多个目录取文件 / 工作台数据放在哪里 / 是否物理合并目录
- 做了什么：核对 `extraResources`、启动层 profile 组合、`DSH_HOME` 注入和插件商店存储路径，区分源码边界、安装资源边界与用户数据边界；确定 MCP 基础配置留在桌面核心，工作台和插件商店继续独立维护，发布时由桌面打包层统一收集。

- 评价：物理合并所有源码会削弱插件边界、增加后续插件商店重做和上游升级的拆分成本；当前更值得做的是统一 workspace/build manifest、安装包布局检查和数据迁移/备份规范。

## C0057 · MCP 配置应归桌面核心设置而不是插件商店

- 场景/触发词：工作台不能配置 MCP / 独立设置菜单 / 插件商店后续重做 / dsh-mcp-client
- 做了什么：复用官方 settings.section 与 settingsScope，把服务器清单写入 `dsh-mcp` 命名空间；启动层读取同一 settings 文件并生成官方 MCP client rows；配置变更按 restart 生效。
- 结果：MCP UI、持久化和运行时组合边界独立于 `dsh-workbench`，后续插件商店重做不会牵连 MCP 基础能力；stdio 和 Streamable HTTP 共享一套校验与 row 映射。
- 评价：MCP 是运行时能力配置，不应依赖插件市场的生命周期；设置页只负责可审计配置，实际工具注册仍交给官方桥接插件。环境 ACL 导致完整构建不可运行时，保留语法检查结果和真实阻塞，不把未执行写成通过。

## C0003 · signal timed out 排查方法论

- 场景/触发词：第 N 个会话卡死 / 历史加载失败 / signal timed out

## C0017 · 逐句 groundedness 的轻量实现路径

- 场景/触发词：R3 / 逐句审计 / groundedness / 引用修正 / 未验证 / 自动修正
- 做了什么：句级评分 = 断言句检测（断言词/数字启发式）+ 证据匹配（中文字/词重叠，可选本地 BGE 余弦取 max），分 grounded/weak/uncited/unsupported 四档；失败后只自动修正一次（LLM 重写优先，规则兜底：补引用、把错引替换成证据匹配更高的条目、实在无证据标“未验证”），再审计并把逐句结果写入 knowledge_audit trace；`run-groundedness-eval.mjs --generate/--gate` 提供 20+ 样本与 ≥0.85 的失败退出门禁
- 结果：进程内自检通过（fully-cited=1.00、flawed 修正后 violations=1 并标未验证、traces 落库）；hybrid 评分待桌面应用内复验
- 评价：规则评分离线可跑、零依赖，但语义匹配有限，生产建议 hybrid（本地 BGE 余弦）+ LLM 修正兜底；auto-fix 只做一次避免模型反复改写；审计结果必须落 trace，否则在线汇总无从采样；注意 `missing` 是数组，`!missing` 恒为假——deep audit 的 valid/abstainRequired 要按数组长度判断

## C0020 · 逐句 groundedness 门禁校准（首轮 0.829 → 1.0）

- 场景/触发词：groundedness 门禁不达标 / 逐句误判 / 引子句 / 未验证句 / LLM 修正不彻底
- 做了什么：用真实 20 题跑桌面门禁，首轮 0.829；逐条看失败句后校准：① 以“是：/包括：”结尾的引子句不算结论句；② 已标“（未验证）/无法确认”的句子计 abstain，不进分母也不计违规；③ weak 句用 LLM 二值判定（supported→grounded，否则→unsupported）；④ LLM 修正后规则兜底总补跑一次，unsupported 句强制标“未验证”；⑤ 修正匹配前把原文与句子的空白统一，否则换行会把句子拆成“句+引用”两段导致 includes 匹配失败；⑥ 在线汇总从 trace 逐句统计（不能只统计编排审计）
- 结果：校准后 20/20 题 rate=1，33 个逐句样本 groundedness=1.0，门禁通过；auditLevel 已切 ref+groundedness

## C0022 · LLM 评估器的三个稳定性坑

- 场景/触发词：LLM 评估 / completeness / 门禁不达标 / 评分恒 0 / 空返回 / 诚实 abstain
- 做了什么：实现 completeness（LLM 打分）、faithfulness（=逐句 groundedness）、缓存命中率、真实调用计数，并建离线/真实运行双门禁；调试中踩到三个坑：① JS 里 `Number(null)===0`，评分器返回 null 被存成 0 分，看似"答案质量差"实为解析失败；② 评估调用 maxTokens 设 20 时模型频繁空返回，必须用 256 以上并加重试；③ 完整度评分器最初按"回答是否覆盖问题所有要点"打 0，但问题要点在知识库中没有时，诚实的"（未验证）"才是合格回答——评分口径必须改为"对照知识条目可答要点评估，诚实 abstain 不算遗漏"，且只传精简条目摘要而非整块

- 做了什么：确认短路径 worktree 已成功创建且 Codex 真实启动；读取官方 Bundle 配置后发现默认 `never` 会拒绝命令/文件审批，备份 profile patch 并切换到显式 `approve-for-me`。
- 结果：真实 provider/轨道证据成立，写型验收因权限未加载暂未完成；原项目未变，测试 worktree 已清理。
- 评价：provider、cwd 隔离和权限模式是三条独立能力链；验证写操作必须在重启后检查实际 Profile 配置，不能仅凭 worker 走到轨道 B 推断可写。
## C0075 · Worktree 写入验收应独立于主代理审计终态

- 场景/触发词：F6 写型 worker、Codex `approve-for-me`、主代理 running、groundedness 审计、apply/discard。
- 做了什么：把验收条件拆成 worker `completed + worktreeStatus=changed`、原项目 apply 前不变、apply 后可见、discard/清理；脚本不再要求主代理先进入 review。
- 结果：真实 Codex 在短路径 worktree 创建目标文件并完成 apply/discard；主代理知识审计或终态延迟不再遮蔽写型闭环证据；测试标记已从原项目删除，孤立分支已清理。
- 评价：编排主报告、知识质量审计和 worktree 写入是独立生命周期；写型能力应以文件/Git 状态为事实源，apply 后必须显式清理测试产物。

## C0076 · 重启后的真实验收要保持证据分层

- 场景/触发词：电脑重启、独立 CDP、F6-A/F6-B、worktree 边界验收。
- 做了什么：重新启动带 `9226` 的桌面实例后复跑真实 Codex 写型闭环；同时复跑双轨 worktree 与路由 smoke，并单独更新计划中的 F6-A/F6-B 状态。
- 结果：F6-A 的 provider、短路径、隔离、apply/discard 证据在重启后仍成立；F6-B 的失败/停止/越界/冲突只保留专项 smoke 证据，未扩大为真实 GUI 全通过。
- 评价：恢复任务中“重启后真实复验”“专项 smoke”“边界未覆盖”必须分栏记录，避免一次成功的主链路验收掩盖剩余风险。

## C0077 · 安全边界错误不能统一返回 500

- 场景/触发词：F6-B、worktree 路径越界、非工作台分支、非法 apply 状态、真实 CDP 验收。
- 做了什么：为 worktree 路由增加独立错误分类：路径/分支越界返回 403，worktree 状态冲突返回 409；新增真实边界脚本覆盖取消清理和三类拒绝。
- 结果：桌面 API 真实返回越界 403、非工作台分支 403、非法 apply 状态 409；取消后的 worktree 可删除。实际 apply 冲突仍未单独构造。
- 评价：安全拒绝和服务端故障必须有稳定可审计的状态码，否则前端会把预期保护误显示为系统异常；验收脚本应断言精确状态码。

## C0078 · Worktree 清理要先核对 Git 注册状态

- 场景/触发词：F6-B 收尾、短路径根目录、空历史目录、测试清理。
- 做了什么：先检查目标目录为空，再对用户仓库执行 `git worktree list` 确认它未被注册，最后只删除精确的空子目录。
- 结果：历史空目录已清理，`C:\dsh-wt` 根目录、用户项目和已注册 worktree 保持不变。
- 评价：worktree 清理不能只看目录名；删除前必须同时核对目录内容和 Git 注册状态，避免误删仍被 Git 管理的隔离区。

## C0079 · 冲突验收应通过 Host 权限链恢复原文件

- 场景/触发词：F6-B apply 冲突、用户项目 ACL、Node EPERM、桌面 Host fs API。
- 做了什么：把 `git apply --check` 失败归类为 409 状态冲突；冲突脚本读取并保存已有文件，通过桌面 Host API 制造冲突，再恢复原文，避免本地脚本直接写入用户项目。
- 结果：Host 修复、脚本语法和专项 smoke 已通过；真实冲突验收因调试实例重启后没有在线项目上下文而暂停，未改动用户项目。
- 评价：涉及用户项目的真实验收必须沿用应用自身权限链；调试实例重启后要先确认项目会话，再运行依赖 `projectPath` 的脚本。

## C0080 · 没有在线会话时不能伪造 worktree 验收上下文

- 场景/触发词：调试实例重启、无活动会话、无 `projectPath`、F6-B 冲突验收。
- 做了什么：脚本增加从当前会话 `cwd/projectPath` 的回退读取，并在任务列表和会话上下文都为空时直接停止。
- 结果：确认当前实例没有可用项目路径和 `sourceSessionId`，未创建任务或修改用户项目。
- 评价：真实 GUI 验收的项目路径、在线主会话和任务作用域必须来自当前应用上下文；已知目录不能替代在线会话证据。

## C0081 · Provider 写入持续运行时不要强杀清理

- 场景/触发词：F6-B apply 冲突、Codex worker running、写入审批等待、测试 worktree 占用。
- 做了什么：在线项目会话中启动冲突验收；发现 worker 未完成写入就停止等待，保留任务和目录占用事实，不强杀 provider 进程。
- 结果：worktree 已创建但无改动，未进入 apply，原项目未修改；测试目录暂被运行中的 provider 占用。
- 评价：外部 provider 卡在审批或运行态时，强制删除可能破坏进程和 Git 元数据；应先保留阻塞证据，待进程自然结束后定点清理。

## C0082 · F6 验收必须绑定在线 Git 项目

- 场景/触发词：F6-B apply 冲突、调试窗口切换项目、`git rev-parse` 失败、非 Git 工作区。
- 做了什么：继续运行冲突脚本时沿用当前在线会话路径；Host 在 Git 前置检查失败后拒绝执行并自动清理任务。
- 结果：当前项目 `D:\临时学习` 非 Git 仓库，未创建 worktree、未修改文件；目标 Git 项目现有 worktree 未变化。
- 评价：真实 worktree 能力不能用另一个目录或手工替换 `projectPath` 代验；项目、会话和 Git 根目录三者必须一致。

## C0083 · 冲突验收要修改可恢复的已跟踪文件

- 场景/触发词：F6-B apply 冲突、Host fs API、测试临时文件清理、Windows 删除权限。
- 做了什么：冲突脚本读取已有 `.gitignore` 基线，让 Codex worker 在隔离 worktree 追加标记，再通过 Host fs/write 在原项目追加不同标记；apply 前先由 Git 检查冲突，finally 恢复原文并 discard/remove 任务。
- 结果：真实 GUI worker 完成并产生改动，apply 返回 409，原项目冲突内容未被覆盖；`.gitignore` 恢复、worktree 和编排均清理，未留下新的测试文件。
- 评价：没有删除 API 时不要创建新的原项目临时文件；优先选择已有且可精确恢复的受版本控制文件，并把恢复放在 finally。
